Where Dev Mail Goes

A decision record about outbound email, reduced to one page and one rule: only production is allowed to touch a real mailbox.

Production sends real email through Amazon SES.

Development sends fake email to Mailpit, a throwaway inbox in Docker.

The dev tier holds no AWS credentials at all. That absence is what stops a dev build from mailing a real person.

the question

What does “dev” even mean for email?

Setting up the AWS account that would send the app’s mail forced a question nobody had answered yet.

Every other dependency has a dev copy. A dev database is easy — it is just another database. A dev mail sender is not, because mail leaves the building.

the constraint

The obvious plan rested on something that isn’t true

The obvious plan was to give dev its own SES user and keep that user in sandbox mode forever. Sandbox only lets you mail addresses you have verified in advance. It fails closed, so it looked like a good safety net.

But sandbox is not a property of a user. It is a property of an AWS account, in one region. Turn it off for production — which you must, to mail real people — and it is off for every key in that account.

So this was never an IAM question. It is an account question, and that has only three answers.

the options

Three answers, one chosen

A AWS for production only. Dev gets a fake mailbox.chosen Dev holds nothing that could reach AWS. Cheapest, and it fits the seam we already built.
B Two AWS accounts, one per tier. The strongest isolation, and the only option where dev can receive real mail. Rejected on cost, not on merit — it is two of everything to create, bill and keep in sync. Recorded as the upgrade path: if dev ever needs real inbound, we replace this record rather than bend it.
C One account, dev in a second region. Looks like parity, isn’t. Same account, so the same keys — and dev would run in a region production never uses, which hides exactly the mistakes dev is supposed to catch.
the design

One function, two adapters

Every part of the app sends mail by calling one function, sendEmail(). Nothing else knows who delivers it. Swapping the delivery is exactly what that seam was built for.

the guardrails

Two mistakes we refuse to allow

A dev build that mails real people. A prod build that quietly drops every message into a sink. Both are stopped by failing loudly, not by good intentions.

  • Dev holds no AWS credentials. Not a policy someone can get wrong — an absence. There is nothing for a misconfiguration to pick up.
  • The provider is set explicitly, with no default. Unset or unrecognised means the app refuses to boot. A default is how the wrong provider gets picked in the environment nobody checked.
  • Boot checks the two against each other. Any AWS credential present means the provider must be SES. Mailpit plus any AWS credential refuses to start. The credentials and the provider setting live in different files, so this is a real cross-check.
  • NODE_ENV is deliberately not the switch. The Dockerfile hardcodes it to production and one image ships to both tiers, so it reads production in dev too.
  • Prod secrets use their own encryption key. Dev’s key cannot decrypt them.
inbound

Dev receives no mail either

Dev publishes no MX record and runs no receipt rules. Nobody can send it anything.

The webhook that handles incoming mail is tested with synthetic fixtures instead. Each one is re-signed at test time with a local test key, so the real signature verifier runs for real rather than being stubbed out. There are negative fixtures for each control it enforces — a lookalike certificate host, an old signature version, an unknown topic, a signature made with the wrong key.

The production topic is never pointed at dev. That is the obvious shortcut, and it would carry real mail into a tier that is assumed to hold none.

the trade

What we gave up, and where we make it back

Dev never touches the real SES path. A DKIM record, an IAM policy or a region mistake will not surface in dev. That is a genuine loss and it is worth naming.

The answer is that the production account’s own sandbox is the integration environment. We prove the real path there — sending, the denied-send checks, the bucket permissions, the retention rule — before asking AWS for production access. While it is still in sandbox, a mistake reaches a developer’s own inbox rather than a stranger.

There is no staging account, and none is wanted.

still open

Honest loose ends

Dev’s namespace has no outbound network policy

Checked and confirmed absent. Until it lands, containment of the dev tier rests on the missing credentials alone. Raised as a follow-up issue.

Mailpit is an unauthenticated store of real-looking data

It keeps whole messages, including any real-looking links they contain. So: its UI requires a login, retention is capped, and production data is never restored into dev.

The DMARC report address isn’t chosen

It needs a real mailbox that accepts SMTP, and it can’t be either of our mail hosts. Terraform omits the tag entirely until one exists — an empty value is worse than none. Enforcement doesn’t depend on it; only visibility does.
